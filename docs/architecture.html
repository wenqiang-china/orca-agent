Architecture Overview

Orca Agent is built as a modular Rust workspace with 19 crates. The architecture prioritizes isolation, fault tolerance, and semantic awareness.

Overview

Orca Agent is built as a modular Rust workspace with 19 crates. The architecture prioritizes isolation, fault tolerance, and semantic awareness.

Crate Layout

orca (CLI + TUI)
├── orca-core # Agent loop, session management
│ ├── orca-providers # Unified provider trait + routing
│ │ ├── orca-deepseek # DeepSeek provider
│ │ ├── orca-anthropic # Anthropic/Claude provider
│ │ └── orca-openai # OpenAI provider
│ ├── orca-tools # Tool executor + registry
│ │ ├── orca-sandbox # OS-level sandboxing
│ │ ├── orca-name-resolver # Fuzzy tool name matching
│ │ └── orca-arg-repair # JSON argument repair
│ ├── orca-capacity # Semantic state + checkpoints
│ ├── orca-seam # Layered context archiving
│ ├── orca-checkpoint # Session persistence
│ ├── orca-loop-guard # Repetition detection
│ └── orca-events # SQLite event store
├── orca-tui # ratatui rendering
├── orca-mcp # MCP client
└── orca-config # TOML configuration

Data Flow

  1. User sends a message via CLI or TUI
  2. orca-core creates the agent loop and sends the message to the configured provider
  3. The provider (DeepSeek/Anthropic/OpenAI) returns either a text response or tool calls
  4. Tool calls are resolved by orca-name-resolver (fuzzy matching), arguments repaired by orca-arg-repair
  5. orca-sandbox enforces OS-level isolation before execution
  6. Tool results are fed back to the provider for the next step
  7. Loop continues until the provider returns a final text response or budget/iteration limits are hit

CanonicalState (Capacity Control)

CanonicalState tracks the semantic state of the conversation across the entire session. It monitors four dimensions:

  • Goals — Active, completed, and failed objectives
  • Constraints — Hard rules that must not be violated
  • Facts — Known information with provenance tracking
  • Open Loops — Pending work items with priority

Three evaluation checkpoints guard the agent loop:

  1. PreRequest — Before each model call: checks context usage, goal count, iteration limits
  2. PostTool — After tool execution: verifies state consistency
  3. ErrorEscalation — On errors: tracks consecutive failures, triggers escalation

LoopGuard

LoopGuard detects and prevents the agent from getting stuck in repetitive tool call patterns.

  • Sliding window analysis (default window: 6 calls)
  • Mutation-aware clearing — write operations reset read-only tracking
  • Graduated response: Allow → SuppressWithCorrection → SuppressSilently → Block
  • Per-tool consecutive failure tracking with automatic blocking

Seam Manager (Context Archiving)

The Seam Manager implements a four-layer compression system to manage context window usage:

Layer Time Window Compression Max Length
Recent 0–10 min None Full
Warm 10–30 min 50% 2000 chars
Cool 30 min – 2 hr 30% 500 chars
Cold 2+ hours 10% 200 chars
Anchor Preservation
User-defined anchors (goals, decisions, constraints) are never compressed. They persist across all layers.

Tool Name Resolution

Tool name resolution uses a 5-step fuzzy matching algorithm. See the Tools page for full details.

Checkpoints

Sessions can be saved to disk and resumed later. Checkpoints preserve the full agent state: message history, tool results, cost tracking, and iteration count.

$ orca resume <checkpoint-id>

Checkpoints are created automatically at session end and can be manually triggered with /checkpoint during a session.
